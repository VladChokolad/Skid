## Часть 1 — Основные понятия

### Ветки (branches)
Ветка — это параллельная версия кода. Представь что у вас есть рабочая тетрадь (main), и каждый раз когда начинаешь новую фичу — делаешь ксерокопию и работаешь в ней. Когда готово — вклеиваешь обратно.

```
main          ←── всегда рабочий код, то что в продакшене
  └── develop ←── общая ветка разработки
        ├── feature/auth       ←── Михаил делает авторизацию
        └── feature/ui-login   ←── Влад делает экран логина
```

### Золотое правило
**Никогда не пишите напрямую в `main`.** Только через pull request.

## Часть 2 — Рабочий процесс (workflow)

### Шаг 1 — Начало работы над фичей

Всегда начинай с актуального кода:

```bash
git checkout develop        # переключиться на develop
git pull                    # получить последние изменения от Влада
git checkout -b feature/название-фичи   # создать новую ветку
```

Примеры названий веток:
```
feature/auth-jwt
feature/party-creation
feature/calculator
fix/debt-calculation-bug
```

### Шаг 2 — Работа над фичей

Пиши код. Делай коммиты часто — после каждого логического шага:

```bash
git add .
git commit -m "тип: что сделал"
```

**Форматы сообщений коммитов:**
```
feat: добавил авторизацию через JWT
fix: исправил расчёт долгов при SplitShares
refactor: вынес логику калькулятора в отдельный пакет
docs: добавил комментарии к структурам
test: добавил тесты для калькулятора
chore: обновил зависимости
```

Плохие сообщения:
```
fix          ← непонятно что именно
изменения    ← бессмысленно
ааа          ← вообще нет
```

### Шаг 3 — Отправить на GitHub

```bash
git push origin feature/название-фичи
```

### Шаг 4 — Создать Pull Request

Заходишь на GitHub → видишь свою ветку → нажимаешь "Compare & pull request".

Заполняешь:
- **Название** — что сделал (например "Добавил авторизацию через JWT")
- **Описание** — что изменилось, как тестировать, скриншоты если есть
- **Reviewer** — добавляешь Влада (или он тебя)

### Шаг 5 — Код-ревью

Влад смотрит твой код и либо:
- Одобряет (Approve) → можно мержить
- Оставляет комментарии → ты правишь, пушишь, он смотрит снова

### Шаг 6 — Merge

После одобрения мержишь ветку в `develop`. На GitHub есть кнопка "Merge pull request".

После мержа удали ветку — она больше не нужна:
```bash
git branch -d feature/название-фичи
```

## Часть 3 — GitLens в VS Code

### Где смотреть историю

**Панель Source Control** (Ctrl+Shift+G) — видишь все изменённые файлы, можешь делать коммиты прямо отсюда без терминала.

**GitLens: Commits** — в боковой панели появляется история всех коммитов. Кликаешь на коммит — видишь что изменилось.

**GitLens: File History** — правой кнопкой на файл → "Open File History". Видишь как конкретный файл менялся со временем.

### Inline blame

Самая полезная фича GitLens — прямо в редакторе рядом с каждой строкой кода видно кто и когда её написал:

```go
func Calculate(party Party) []Settlement {  // Михаил, 2 дня назад
    balances := make(map[int]float64)       // Михаил, 2 дня назад
```

Наводишь на строку — появляется подсказка с полным коммитом. Очень удобно когда нужно понять "зачем это тут написано".

### Сравнение веток

GitLens → "Search & Compare" → "Compare References" → выбираешь две ветки. Видишь все различия между ними.

### График веток

Устанавливаешь **Git Graph** (отдельное расширение) → внизу появляется кнопка "Git Graph". Открывается визуальное дерево всех веток и коммитов.

## Часть 4 — Типичные ситуации

### Влад запушил изменения, ты хочешь их получить

```bash
git checkout develop
git pull
```

Если ты в своей ветке и хочешь получить последние изменения из develop:

```bash
git checkout feature/твоя-ветка
git merge develop
```

### Конфликт — вы оба изменили один файл

Git покажет:
```
<<<<<<< HEAD
твой код
=======
код Влада
>>>>>>> develop
```

Нужно вручную решить что оставить. В VS Code это удобно — он подсвечивает конфликты и предлагает кнопки "Accept Current", "Accept Incoming", "Accept Both".

После разрешения:
```bash
git add .
git commit -m "fix: разрешил конфликт в models.go"
```

### Случайно закоммитил не то

Отменить последний коммит (изменения остаются):
```bash
git reset --soft HEAD~1
```

Отменить изменения в конкретном файле:
```bash
git checkout -- filename.go
```

### Посмотреть что изменилось

```bash
git status          # какие файлы изменены
git diff            # что именно изменилось в файлах
git log --oneline   # история коммитов
```

## Часть 5 — Договорённости для Skid

### Структура веток
```
main      ← продакшн, только рабочий код
develop   ← общая разработка
feature/* ← новые фичи
fix/*     ← исправление багов
```

### Правила
1. Никогда не пушим напрямую в `main` и `develop`
2. Каждая фича — отдельная ветка
3. Перед созданием ветки — `git pull` из `develop`
4. Pull request обязателен даже если "маленькое изменение"
5. Коммиты делаем часто — лучше 10 маленьких чем один огромный
6. Сообщения коммитов на русском или английском — главное одинаково

### Разделение ответственности
```
backend/    ← Михаил
frontend/   ← Влад
README.md   ← оба
```

Если нужно изменить что-то в зоне ответственности другого — обязательно обсуждаем сначала.

### Синхронизация
Договоритесь созваниваться раз в день (или в Telegram) чтобы:
- Синхронизировать что сделано
- Согласовать формат API (что бэкенд отдаёт, что фронтенд ожидает)
- Решить конфликты до того как они появятся в коде
